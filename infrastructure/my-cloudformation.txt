================================================================================

USER QUESTION:
Based on this interface, what would a cloudformation template for a dynamodb
look like? Can the cloud formation template specify field and database names?
Can you provide a file with seed data to populate the database with
cloudformation?

TypeScript Interface:
```typescript
export interface PhoneNumber {
  id?: number;
  type: 'home' | 'work' | 'mobile';
  number: string;
}

export interface Friend {
  id?: number;
  friendName: string;
  phoneNumbers: PhoneNumber[];
}
```

ANSWER:
Yes, CloudFormation can specify table names and key attribute names, but
DynamoDB is schema-less for non-key attributes.

FILES CREATED:
1. infrastructure/dynamodb-stack.yaml - CloudFormation template
2. infrastructure/seed-data.json - Sample data in DynamoDB JSON format
3. infrastructure/deploy.sh - Deployment script
4. infrastructure/README.md - Complete documentation

KEY POINTS:
- CloudFormation CAN specify: Table name, key attributes (id, friendName)
- CloudFormation CANNOT specify: Non-key fields (DynamoDB is schema-less)
- Seed data: Must be loaded via AWS CLI, Lambda, or SDK (not CloudFormation)

DYNAMODB SCHEMA DESIGN:
- Primary Key: id (String) - Partition key
- Attributes: friendName (String), phoneNumbers (List), createdAt, updatedAt
- Global Secondary Indexes:
  * FriendNameIndex - Query by name
  * CreatedAtIndex - Sort by creation date
- Billing: PAY_PER_REQUEST (on-demand, no capacity planning)
- Features: Point-in-time recovery, KMS encryption, DynamoDB Streams

DYNAMODB JSON FORMAT:
DynamoDB uses typed JSON with attribute markers:
- S = String
- N = Number (stored as string)
- L = List
- M = Map
- BOOL = Boolean

Example Item:

```json
          "type": { "S": "mobile" },
```

QUESTION 2: Stack Organization - Separate vs Combined Templates
================================================================================

USER QUESTION:
For the API Gateway + Lambda layer, should those be separate templates or
part of the dynamodb-stack template? What is best practice? I assume that
the lambda function is dependent on the dynamodb creation and seeding and
that the api gateway is then dependant on the lambda functions. Is this
correct? What is best practice?

ANSWER:
Your dependency analysis is CORRECT:
  DynamoDB Table (created)
      ↓
  Lambda Functions (depend on TableName/Arn)
      ↓
  API Gateway (depends on Lambda ARN)

Note: Lambda depends on table existence, NOT seeding (seeding is operational)

================================================================================
BEST PRACTICE: SEPARATE STACKS WITH CROSS-STACK REFERENCES
================================================================================

RECOMMENDED ARCHITECTURE:
```
Stack 1: dynamodb-stack.yaml (database layer)
   ↓ exports TableName, TableArn
Stack 2: lambda-stack.yaml (business logic layer)
   ↓ imports DynamoDB exports, exports Lambda ARNs
Stack 3: api-gateway-stack.yaml (API layer)
   ↓ imports Lambda ARNs
```

ADVANTAGES OF SEPARATE STACKS:
1. Independent Lifecycle - Update API without touching database
2. Reusability - Multiple APIs can reference same Lambda/DynamoDB
3. Blast Radius - Failed Lambda deployment won't risk database deletion
4. Team Ownership - Different teams can own different layers
5. Faster Iterations - Change API config without full stack updates
6. Rollback Safety - Rollback API changes without affecting data
7. Environment Flexibility - Dev API can point to shared dev database

DISADVANTAGES:
1. Slightly more complex to manage multiple stacks
2. Need to handle cross-stack reference deletion order
3. More CloudFormation API calls

WHEN TO USE SINGLE MONOLITHIC STACK:
- Very small projects (< 5 resources)
- Tightly coupled resources that always deploy together
- Proof-of-concept or learning projects
- You want simplicity over flexibility

CROSS-STACK REFERENCE PATTERN:

dynamodb-stack.yaml (exports):
```yaml
Outputs:
  TableName:
    Value: !Ref FriendsTable
    Export:
      Name: !Sub '${AWS::StackName}-TableName'
  TableArn:
    Value: !GetAtt FriendsTable.Arn
    Export:
      Name: !Sub '${AWS::StackName}-TableArn'
```

lambda-stack.yaml (imports from DynamoDB):
```yaml
Parameters:
  DatabaseStackName:
    Type: String
    Default: friends-app-stack
    Description: Name of the DynamoDB stack to import from

Resources:
  GetFriendsFunction:
    Type: AWS::Lambda::Function
    Properties:
      Environment:
        Variables:
          TABLE_NAME: !ImportValue
            Fn::Sub: '${DatabaseStackName}-TableName'
```

api-gateway-stack.yaml (imports from Lambda):
```yaml
Parameters:
  LambdaStackName:
    Type: String
    Default: friends-lambda-stack

Resources:
  GetFriendsIntegration:
    Type: AWS::ApiGatewayV2::Integration
    Properties:
      IntegrationUri: !ImportValue
        Fn::Sub: '${LambdaStackName}-GetFriendsArn'
```

DEPLOYMENT ORDER:
```bash
# 1. Database (once, rarely changes)
aws cloudformation deploy \
  --stack-name friends-db-stack \
  --template-file 01-dynamodb-stack.yaml

# 2. Lambda (updates when business logic changes)
aws cloudformation deploy \
  --stack-name friends-lambda-stack \
  --template-file 02-lambda-stack.yaml

# 3. API Gateway (updates when API contract changes)

  --stack-name friends-api-stack \
  --template-file 03-api-gateway-stack.yaml
```

ALTERNATIVE: NESTED STACKS (MIDDLE GROUND)
Use a master template that orchestrates child templates:

```yaml
# master-stack.yaml
Resources:
  DatabaseStack:
    Type: AWS::CloudFormation::Stack
    Properties:
      TemplateURL: s3://bucket/dynamodb-stack.yaml

  LambdaStack:
    Type: AWS::CloudFormation::Stack
    DependsOn: DatabaseStack
    Properties:
      TemplateURL: s3://bucket/lambda-stack.yaml
      Parameters:
        TableName: !GetAtt DatabaseStack.Outputs.TableName
```

When to use nested stacks:
- Want logical separation but single deployment command
- Need explicit dependency ordering via DependsOn
- Sharing templates across environments

Disadvantages:
- Must upload templates to S3 first
- All stacks still update together
- More complex than separate stacks

QUESTION 3: Stack Deletion for Cost Management
================================================================================

USER QUESTION:
When you need to take down a whole stack for financial purposes, is it easy
in AWS to take down each stack, so if I took down the api gateway stack, then
the lambda stack, and then the dynamodb stack, how would you do it? Would you
have to take them down separately or like other full stacks, delete the stack
and all resources are deleted with it?

ANSWER:
Each stack deletes as a unit—all resources in that stack are removed together.
You delete them separately in REVERSE dependency order.

================================================================================
HOW STACK DELETION WORKS
================================================================================

When you delete a CloudFormation stack:
```bash
aws cloudformation delete-stack --stack-name friends-api-stack
```

CloudFormation automatically:
1. Identifies all resources in that stack
2. Deletes them in reverse creation order
3. Handles dependencies within the stack
4. Removes the stack once all resources are gone

ONE COMMAND = ENTIRE STACK GONE
(API Gateway, routes, integrations, Lambda functions, etc.)

DELETION ORDER (REVERSE DEPENDENCY):
```bash
# 1. Delete API Gateway stack (top layer, no dependencies)
aws cloudformation delete-stack --stack-name friends-api-stack

# Wait for completion (30-60 seconds typically)
aws cloudformation wait stack-delete-complete --stack-name friends-api-stack

# 2. Delete Lambda stack (middle layer)
aws cloudformation delete-stack --stack-name friends-lambda-stack
aws cloudformation wait stack-delete-complete --stack-name friends-lambda-stack

# 3. Delete DynamoDB stack (bottom layer - contains your data!)
aws cloudformation delete-stack --stack-name friends-db-stack
aws cloudformation wait stack-delete-complete --stack-name friends-db-stack
```

WHY REVERSE ORDER?
If you try to delete DynamoDB first while Lambda still references it:
❌ Delete will FAIL
Error: "Export friends-db-stack-TableName cannot be deleted as it is in use"

You MUST delete consumers before providers.

QUICK TEARDOWN SCRIPT:
```bash
#!/bin/bash
# infrastructure/teardown.sh

STACKS=(
  "friends-api-stack"      # Delete first (top of dependency chain)
  "friends-lambda-stack"   # Delete second
  "friends-db-stack"       # Delete last (bottom of chain)
)

for stack in "${STACKS[@]}"; do
  echo "Deleting $stack..."
  aws cloudformation delete-stack --stack-name "$stack"
  aws cloudformation wait stack-delete-complete --stack-name "$stack"
  echo "✓ $stack deleted"
done

echo "All stacks deleted!"
```

================================================================================
SELECTIVE SHUTDOWN OPTIONS (COST SAVING)
================================================================================

OPTION 1: DELETE TOP LAYERS ONLY (KEEP DATA)
```bash
# Delete API + Lambda (no ongoing costs when idle)
aws cloudformation delete-stack --stack-name friends-api-stack
aws cloudformation delete-stack --stack-name friends-lambda-stack

# Keep DynamoDB with data (minimal storage cost ~$0.25/GB/month)
# DynamoDB on-demand only charges for actual reads/writes
```

Costs when API/Lambda deleted but DynamoDB kept:
- DynamoDB storage: ~$0.25/GB/month
- Point-in-time recovery: ~$0.20/GB/month
- No compute costs (Lambda gone, no requests hitting DynamoDB)

OPTION 2: BACKUP DATA, DELETE EVERYTHING
```bash
# 1. Backup DynamoDB to S3
aws dynamodb create-backup \
  --table-name friends-app-table-dev \
  --backup-name friends-backup-$(date +%Y%m%d)

# Or export to S3 (better for large tables)
aws dynamodb export-table-to-point-in-time \
  --table-arn arn:aws:dynamodb:region:account:table/friends-app-table-dev \
  --s3-bucket my-backup-bucket

# 2. Delete all stacks
./teardown.sh

# 3. Later: Restore from backup
aws dynamodb restore-table-from-backup \
  --target-table-name friends-app-table-dev \
  --backup-arn <backup-arn>
```

COST COMPARISON:

Scenario                                    | Monthly Cost (approx)
--------------------------------------------|----------------------
All 3 stacks running, no traffic            | ~$0.50 (storage only)
All 3 stacks running, moderate traffic      | ~$5-20 (requests + data)
API + Lambda deleted, DynamoDB kept         | ~$0.25-0.50 (storage)
All stacks deleted                          | $0

KEY INSIGHT: Lambda and API Gateway are pay-per-request with ZERO cost when
idle! DynamoDB on-demand is similar but has small storage costs.

================================================================================
PROTECTION: PREVENT ACCIDENTAL DELETION
================================================================================

Add to your stacks:
```yaml
# In dynamodb-stack.yaml (to protect data)
Resources:
  FriendsTable:
    Type: AWS::DynamoDB::Table
    DeletionPolicy: Retain        # Keep table even if stack deleted
    UpdateReplacePolicy: Retain   # Keep table on replacement updates
    Properties:
      # ... existing config
```

With DeletionPolicy: Retain:
- Delete stack → DynamoDB table SURVIVES as orphaned resource
- Must manually delete table later via console/CLI
- Good for production data protection

COMMON DYNAMODB OPERATIONS (FROM README)
================================================================================

ADD A NEW FRIEND:
```bash
aws dynamodb put-item \
  --table-name $TABLE_NAME \
  --item '{
    "id": {"S": "friend-006"},
    "friendName": {"S": "John"},
    "phoneNumbers": {
      "L": [
        {
          "M": {
            "id": {"N": "601"},
            "type": {"S": "mobile"},
            "number": {"S": "555-000-1111"}
          }
        }
      ]
    },
    "createdAt": {"N": "'$(date +%s)000'"},
    "updatedAt": {"N": "'$(date +%s)000'"}
  }'
```

GET A FRIEND BY ID:
```bash
aws dynamodb get-item \
  --table-name $TABLE_NAME \
  --key '{"id": {"S": "friend-001"}}'
```

UPDATE A FRIEND:
```bash
aws dynamodb update-item \
  --table-name $TABLE_NAME \
  --key '{"id": {"S": "friend-001"}}' \
  --update-expression "SET friendName = :name, updatedAt = :timestamp" \
  --expression-attribute-values '{
    ":name": {"S": "William"},
    ":timestamp": {"N": "'$(date +%s)000'"}
  }'
```

DELETE A FRIEND:
```bash
aws dynamodb delete-item \
  --table-name $TABLE_NAME \
  --key '{"id": {"S": "friend-001"}}'
```

QUERY BY NAME (USING GSI):
```bash
aws dynamodb query \
  --table-name $TABLE_NAME \
  --index-name FriendNameIndex \
  --key-condition-expression "friendName = :name" \
  --expression-attribute-values '{":name": {"S": "Jane"}}'
```

SCAN ALL ITEMS:
```bash
aws dynamodb scan --table-name $TABLE_NAME
```

COUNT ITEMS:
```bash
aws dynamodb scan \
  --table-name $TABLE_NAME \
  --select "COUNT"
```

KEY TAKEAWAYS
================================================================================

1. STACK ORGANIZATION:
   - Use separate stacks for different layers (DB, Lambda, API)
   - Cross-stack references via Exports/Imports
   - Deploy in dependency order: DB → Lambda → API
   - Delete in reverse order: API → Lambda → DB

2. COST MANAGEMENT:
   - Lambda & API Gateway: $0 when idle (pay per request)
   - DynamoDB: Small storage cost even when idle
   - Delete top layers (API/Lambda) to save money but keep data
   - Full deletion: 3 commands, <10 minutes total

3. CLOUDFORMATION CAPABILITIES:
   - Can specify: Table names, key attributes, indexes
   - Cannot specify: Non-key attributes (schema-less)
   - Cannot bulk-load: Use AWS CLI/SDK for seed data

4. BEST PRACTICES:
   - Separate stacks for production flexibility
   - Add DeletionPolicy: Retain for data protection
   - Use cross-stack references for loose coupling
   - Back up data before full teardown

5. DEPLOYMENT:
   - One command per stack
   - Each stack is atomic (all resources or none)
   - Use wait commands to ensure completion
   - Monitor stack events for troubleshooting

================================================================================
API GATEWAY ARCHITECTURE
================================================================================

HTTP API vs REST API:
- Chose HTTP API (API Gateway v2) over REST API
- 70% cheaper ($1/million vs $3.50/million requests)
- Built-in CORS support (no OPTIONS methods needed)
- Simpler configuration
- Automatic deployment on changes
- Native Lambda proxy integration

Route Structure:
  GET    /friends        → GetFriendsFunction    (list all)
  GET    /friends/{id}   → GetFriendFunction     (get one)
  POST   /friends        → CreateFriendFunction  (create)
  PUT    /friends/{id}   → UpdateFriendFunction  (update)
  DELETE /friends/{id}   → DeleteFriendFunction  (delete)

CORS Configuration:
- AllowOrigins: * (all origins - restrict in production)
- AllowMethods: GET, POST, PUT, DELETE, OPTIONS
- AllowHeaders: Content-Type, Authorization
- MaxAge: 300 seconds (5 minutes)

================================================================================
TROUBLESHOOTING COMMON ISSUES
================================================================================

Issue 1: Stack Creation Fails with "Export cannot be deleted as it is in use"
Solution: Delete stacks in reverse order (API → Lambda → DB)

Issue 2: Lambda function times out
Check:
- DynamoDB table exists and is active
- Lambda has correct IAM permissions
- Table name environment variable is set correctly
- Check CloudWatch logs for errors

Issue 3: API Gateway returns 403 Forbidden
Check:
- Lambda permission resource created (allows API Gateway to invoke)
- Integration URI points to correct Lambda ARN
- Stage is deployed (HTTP API auto-deploys by default)

Issue 4: CORS errors in browser
Verify:
- API Gateway CORS configuration allows your origin
- Lambda returns proper CORS headers in response
- Preflight OPTIONS requests work (HTTP API handles automatically)

Issue 5: Seed data won't load
Check:
- jq is installed (brew install jq)
- Seed data JSON is valid (jq . seed-data.json)
- Table name is correct
- DynamoDB permissions in AWS credentials

Issue 6: Cannot delete S3 bucket (Lambda deployment bucket)
Solution: Empty bucket first
```bash
aws s3 rm s3://friends-lambda-deployments-ACCOUNT-dev --recursive
aws cloudformation delete-stack --stack-name friends-lambda-stack
```

Issue 7: Stack stuck in DELETE_IN_PROGRESS
Check:
- Resources that can't be deleted (S3 bucket with objects)
- Resources created outside CloudFormation
- Force delete: retain problematic resources
```bash
aws cloudformation delete-stack \
  --stack-name STACK \
  --retain-resources RESOURCE_LOGICAL_ID
```

Update FriendService to call API:

```typescript
import { Injectable } from '@angular/core';
import { HttpClient, HttpHeaders } from '@angular/common/http';
import { Observable } from 'rxjs';
import { Friend } from './models/friend.interface';

@Injectable({
  providedIn: 'root'
})
export class FriendService {
  // Replace with your API endpoint from stack output
  private apiUrl = 'https://xxxxx.execute-api.us-east-1.amazonaws.com/api/friends';

  constructor(private http: HttpClient) {}

  getFriends(): Observable<{ friends: Friend[], count: number }> {
    return this.http.get<{ friends: Friend[], count: number }>(this.apiUrl);
  }

  getFriend(id: string): Observable<Friend> {
    return this.http.get<Friend>(`${this.apiUrl}/${id}`);
  }

  createFriend(friend: Omit<Friend, 'id' | 'createdAt' | 'updatedAt'>): Observable<Friend> {
    return this.http.post<Friend>(this.apiUrl, friend);
  }

  updateFriend(id: string, friend: Partial<Friend>): Observable<Friend> {
    return this.http.put<Friend>(`${this.apiUrl}/${id}`, friend);
  }

  deleteFriend(id: string): Observable<{ message: string, id: string }> {
    return this.http.delete<{ message: string, id: string }>(`${this.apiUrl}/${id}`);
  }
}
```

Update Component to use Observable:

```typescript
export class FriendListComponent implements OnInit {
  friends: Friend[] = [];
  loading = false;
  error: string | null = null;

  constructor(private friendService: FriendService) {}

  ngOnInit(): void {
    this.loadFriends();
  }

  loadFriends(): void {
    this.loading = true;
    this.error = null;

    this.friendService.getFriends().subscribe({
      next: (response) => {
        this.friends = response.friends;
        this.loading = false;
      },
      error: (err) => {
        console.error('Error loading friends:', err);
        this.error = 'Failed to load friends. Please try again.';
        this.loading = false;
      }
    });
  }
}
```

GitHub Actions Example:

```yaml
# .github/workflows/deploy.yml
name: Deploy AWS Infrastructure

on:
  push:
    branches: [main]
  workflow_dispatch:

env:
  AWS_REGION: us-east-1
  ENVIRONMENT: prod

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Deploy DynamoDB Stack
        run: |
          aws cloudformation deploy \
            --template-file infrastructure/dynamodb-stack.yaml \
            --stack-name friends-app-stack-${{ env.ENVIRONMENT }} \
            --parameter-overrides Environment=${{ env.ENVIRONMENT }} \
            --no-fail-on-empty-changeset

      - name: Deploy Lambda Stack
        run: |
          aws cloudformation deploy \
            --template-file infrastructure/02-lambda-stack.yaml \
            --stack-name friends-lambda-stack-${{ env.ENVIRONMENT }} \
            --parameter-overrides \
              Environment=${{ env.ENVIRONMENT }} \
              DatabaseStackName=friends-app-stack-${{ env.ENVIRONMENT }} \
            --capabilities CAPABILITY_NAMED_IAM \
            --no-fail-on-empty-changeset

      - name: Deploy API Gateway Stack
        run: |
          aws cloudformation deploy \
            --template-file infrastructure/03-api-gateway-stack.yaml \
            --stack-name friends-api-stack-${{ env.ENVIRONMENT }} \
            --parameter-overrides \
              Environment=${{ env.ENVIRONMENT }} \
              LambdaStackName=friends-lambda-stack-${{ env.ENVIRONMENT }} \
            --no-fail-on-empty-changeset

      - name: Get API Endpoint
        run: |
          API_URL=$(aws cloudformation describe-stacks \
            --stack-name friends-api-stack-${{ env.ENVIRONMENT }} \
            --query "Stacks[0].Outputs[?OutputKey=='ApiEndpoint'].OutputValue" \
            --output text)
          echo "API Endpoint: $API_URL"
```
